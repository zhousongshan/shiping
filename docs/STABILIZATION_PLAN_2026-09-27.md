# 本地稳定化与交付实现计划

日期：2026-09-27。状态：实施中；第一批本地改造见 `STABILIZATION_PROGRESS_2026-09-27.md`，未完成项和外部验收条件单独列出。依据 `REAL_STATUS_AUDIT_2026-09-27.md` 及实际失败任务制定。本计划替代旧实施计划的执行顺序；已存在的数据库、账号、Worker、媒体处理代码优先复用，不因列入计划就认定已验收。

## 目标和边界

先在本地完成真实端到端验收，准备可交付的源码、配置和部署文档，再由同事部署。公司环境的部署验收单独记录。

覆盖文字、图片、参考视频的七种非空组合；最多 6 张图片；本地参考视频最长 180 秒、最大 150 MB。支持自动或指定时长，以及横屏、竖屏和方形画幅。自动时长有参考跟随参考，无参考按内容规划；指定时长遵守用户选择。用户指定片段编辑、真人出镜、社交平台链接解析继续列为本轮范围外；制作过程中的定向返修属于本轮。

生成成功、文件可播放、质量通过、最终交付是四个不同事实。每个已生成版本都可查看；只有全部必需检查通过才标记最终完成。不可恢复的异常应给出具体原因、保留结果与回执，进入明确处理状态。

## 已确认的问题及根因

| 问题 | 证据 | 改进方向 |
| --- | --- | --- |
| 同一任务重复执行 | 隔离实验中 1 条任务被分派 2 次；实际日志反复出现会话占用 | 原子执行权、执行版本检查，等待状态和释放执行权一起提交 |
| 状态失真、已失败仍可能有执行器工作 | 本地状态被并行执行者覆盖 | 所有状态更新带执行令牌；过期执行者不能覆盖状态或发起新提交 |
| 查询断线中断整条制作 | 视频已受理甚至成功，本地却因 poll 断线失败 | 已知供应商 ID 直接恢复查询、下载；区分本地执行状态与远端生成状态 |
| 提交不明无法自动核对 | 三次相关任务留有不明回执 | 独立提交账本、幂等和核对能力；无法证实时保留待核对 |
| 审片误判与结果结构错误 | 有音轨却判无音轨；audio evidence 只有 shot_changes；相同视频结论反复 | 确定性检查与语义检查分开；检查结构和证据；限制复查并保留矛盾 |
| Agent 随意尝试下一步 | 未验收就合成、虚构 unit_id、反复请求生成被门槛拦截 | 标准流程由代码推进，模型只返回当前步骤需要的数据 |
| 结果不能立即查看 | 已有两个 mp4，预览接口仍返回 404 | 为每个生成版本提供授权预览和下载接口 |
| 两个替代版本默认一起拼接 | 两版 10 秒素材被拼成 20.06 秒 | 按单元分组，单元内选一个版本，避免混淆替代版本和连续镜头 |
| 参考生成缺外部素材通道 | reference_ready=false | 持久素材地址、签名和供应商实际读取验证 |
| 供应商适配器升级影响旧任务 | 曾因只修改查询恢复逻辑而触发 Provider 变化 | 固定任务使用的适配器版本，显式迁移；替代临时 SHA 白名单 |
| 测试通过但真实流程失败 | 91 项通过、1 项跳过；当前 v2 六条任务无 completed | 增加真实故障复现、隔离端到端验收和人工质量样本 |

## 第一步：修复调度与执行权（最高优先级）

涉及 `app/worker.py`、`app/store.py`、`app/database.py`、`app/agent_runner.py`、`app/recovery.py`。

1. 调度器立即排除当前进程仍在执行的任务 ID，加入已复现问题的回归用例。
2. 增加任务/步骤执行令牌、租约截止时间、心跳与单调递增执行版本。领取、续租、释放及状态迁移使用事务；重要写入校验令牌和版本，过期执行者的写入及新提交被拒绝。
3. `waiting_build` 对外状态与内部执行权分离。保存下次查询时间并释放执行权后才能再次领取；单调度器锁不能替代任务执行锁。
4. 网络中断、质量不合格、检查暂不可用、提交待核对分别存储，不互相覆盖。任务整体状态从步骤状态和待处理原因推导。
5. 保留模型会话 ID、步骤输出和执行中记录。重启先核对执行权与既有回执，再继续；不强删会话锁后重开第二个执行器。
6. 本地默认启动 API 与独立 Worker，并提供统一启动/停止脚本及状态检查。Web 重启不会重跑生成。

验收：同一任务经过排队、等待、恢复、重启，不出现两个有效执行者；延迟到达的旧执行结果不能改写新状态；两个不同任务可交错执行；真实会话占用故障有回归覆盖。

## 第二步：提交、查询、下载和素材通道

涉及 `app/hypit_adapter.py`、`app/recovery.py`、`app/config.py`、`app/media_gateway.py`、`provider-autodl-wan/`；新增供应商提交记录和素材存储接口。

1. 持久化请求摘要、生成尝试 ID、本地 Build ID、供应商任务 ID、受理时间、结果位置、错误阶段、用量预留及实际用量。使用唯一约束和事务保护提交意图，覆盖并发请求检查/写入间隙。
2. 明确区分：尚未发送、发送结果不明、已受理、生成中、远端失败、生成成功、下载完成。供应商成功不自动等于整片通过验收。
3. 已知任务只继续查询或下载原任务。避免将重新创建本地 Build 作为常规查询恢复方式；历史恢复必须验证原回执和固定请求。
4. 查询、下载、理解和审片的连接故障使用有上限的退避重试；下载写临时文件，校验后原子落盘。认证、输入不支持、明确内容失败走不同处理路径。
5. 未知提交保留预算和核对记录。已确认运行量与未知受理量分开显示、限制；旧未知任务不会永远伪装成运行中的任务，也不会被静默当成“没发生费用”。连续未知提交触发提交保护，避免不断新建任务扩大不确定费用。
6. 供应商提供幂等键/客户端请求查询时接入；没有这些能力时，明确保留人工核对分支。管理员处理记录不能伪造未受理事实。
7. 为参考素材配置私有持久存储和可过期签名地址。服务可仍运行在本地，素材地址必须能被外部模型读取。支持 GET/Range，签名有效期覆盖排队和读取；明确错误尽早在提交前显示。
8. 适配器和请求转换按版本固定；查询修复与生成参数变化分开管理。旧任务依原版本恢复，显式记录兼容迁移，去掉临时硬编码摘要特例。

验收：受理后断线/重启仍只有一个供应商任务；查询和下载故障不产生新收费请求；明确拒单与未知提交分类正确；模型真实读取参考素材成功。外部服务缺少核对能力时不得宣称实现了自动对账。

外部条件：持续可用的素材存储/签名地址、供应商权限与额度。缺少条件不妨碍编写和验证本地接口，但参考生成通过必须有实际供应商读取证据。

## 第三步：先把已有结果与进度展示完整

涉及 `app/server.py`、`app/candidate.py`、`static/app.js`、`static/index.html`、`static/style.css`。

1. 增加按生成版本读取的预览/下载接口，校验用户权限、任务归属和文件真实性，不要求任务最终完成。
2. 展示每个生成单元的不同版本、时长、生成状态、检查状态和问题证据。失败页面仍显示已保存的视频。
3. 一个单元内选择一个采用版本；不同单元按计划排序拼接。同一单元两个替代版本不默认全部勾选；需要手动对比拼接时明确提示总时长改变。
4. 区分生成成功、待检查、检查未通过、待核对、最终完成。继续处理按钮说明将执行查询、下载或检查中的哪一步；新的收费返修必须清楚展示。
5. 记录阶段开始/结束及尝试次数，展示排队、理解、规划、提交、远端等待、下载、审片、拼接耗时。恢复后的累计时间与本次尝试时间分别计算。
6. 可用功能由实际服务配置和验收状态决定。参考通道缺失时提前说明；关闭的功能不显示为正常承诺。

验收：任务生成第一个文件后即可播放和下载；重启及质检失败后仍可看；单元的版本选择不改变成片计划总时长；页面状态与实际执行一致。

## 第四步：收紧完整制作流程和质量检查

涉及 `app/agent_runner.py`、`app/workflows.py`、`app/subject_spec.py`、`app/unit_planner.py`、`app/production_schema.py`、`app/unit_review.py`、`app/agent_tools.py`。

1. 以代码驱动标准步骤：输入检查 → 理解主体/参考 → 校验方案 → 提交生成单元 → 查询/下载 → 检查单元 → 选取通过版本 → 合成 → 检查成片 → 交付。模型仅承担理解、内容规划、提示词和有证据的语义检查，不任意控制提交和状态。
2. 每步定义结构化输入、输出和校验规则。保存有效结果以复用，失败只重试当前步骤，禁止从读取任务重新做一遍。
3. 身份、场景、动作、镜头、参考事件、音频要求分别写入制作计划；文字中的新动作不能被原图静态姿态否定。原图作为身份参考还是首帧，由已验证的模型能力和创作意图决定。
4. 文件是否可解码、实际时长/画幅、音轨存在性、近似静音由代码检查。画面语义、动作、主体一致性和声音内容由专门检查步骤判断。
5. 音频观察必须有符合语音/音乐/音效结构的实际证据；空内容、shot_changes 等错误结构不得标 checked=true。无音轨、音轨识别失败和有意无声分开处理。
6. 统一检查结果类型：通过、有证据的不合格、证据不足、检查执行失败。结构错误或接口断线重试检查；证据不足进入有限复查；有证据的不合格才允许预算内定向返修。
7. 每次复查关联具体视频哈希和检查版本；前后矛盾保留并进入仲裁，不靠反复审片直到碰到 pass。摘要必须与检查项和最终状态一致。
8. 自动返修设置次数、费用预留及总时限；只改有问题的单元。失败上限后展示最新候选与未满足项。历史任务预算与新提交记录在升级时保留。
9. 用小鸡样例分辨提示词/图片模式选择问题、供应商能力问题和审片误判。若当前供应商无法满足核心动作或参考需求，先验证替代适配器；不静默降低要求或切换在途任务。

验收：静态视频不能被当作明确舞蹈通过；有音轨的视频不能被确定性检查称为无音轨；审片故障不触发新生成；从提交到合格成片的正常流程无需管理员手动修状态。

## 第五步：补齐七种输入、时长和连续性

涉及 `app/intent.py`、`app/reference_analysis.py`、`app/unit_planner.py`、`app/continuity.py`、`app/compiler.py` 及供应商能力配置。

- 七种输入分别有明确的默认意图与实际制作路线。无文字的图片任务默认展示，参考任务默认保留主要事件；影响主体对应关系的歧义才追问。
- 自动时长保持“有参考跟随参考，无参考按内容规划”。固定时长不可被模型擅自改写；严格与近似容差有明确数字并在技术验收中验证。
- 一次生成允许覆盖多个镜头。超出已验证的单次模型限制或确有内容依赖时才拆段；按语义和事件拆分，不固定按相同秒数机械切块。
- 长参考按时间区间完整分析，记录事件覆盖与片段来源。用户缩短时长与完整保留内容冲突时明确处理，不静默丢掉关键动作。
- 关联片段继承同一主体和通过检查的衔接画面；独立单元在额度允许时并发，存在依赖的单元按顺序执行。
- 合成选用正确单元版本，检查边界、总时长与声音。生成模型输出略超时长时按已验证规则裁切，不依赖再次付费生成修正小数秒误差。

验收：七种输入均有当前版本真实成功样例；自动、8/15/20/30/45/60 秒以及 180 秒参考边界纳入测试矩阵。上传成功和方案写出不算完整样例通过。

2. 设置每用户并发与全局生成额度，公平排队；远端等待释放本地执行槽，同一任务执行权仍唯一。
3. 明确任务记录和文件的备份与迁移。旧任务保持可预览；未知提交记录不丢失；迁移后新产生的回执不能因直接回滚旧库而消失。
4. 提供干净环境安装、配置检查、API/Worker 启停、日志、备份恢复及故障处理说明。源码导出不包含密钥、用户素材和数据库。

验收：2/5/10 个账号提交时不串任务、不越权、不丢任务；实际付费并发仍按供应商额度限制。API/Worker 重启和备份恢复通过。先交付本地通过版本，再形成公司部署验收记录。

## 验证顺序与放行标准

1. 先补齐已复现故障的隔离测试：重复领取、过期执行者写入、收到回执前后崩溃、网络断线、审核结构错误、错误音频证据、版本重复拼接和素材过期。
2. 复用已生成视频验证预览、下载、检查和合成，减少为验证程序而重复生成。
3. 用最小收费闭环验证“文字＋小鸡图片＋10秒户外跳舞”。记录请求、视频、动作证据、音轨、耗时和人工结论；整个流程必须无需后台人工救场。
4. 闭环通过后开展七种输入首轮样例，每种至少 3 条，共至少 21 条；再用覆盖矩阵补齐全部时长、画幅、长参考、歧义、多主体和声音。不得将不同版本或不同供应商旧样例混入当前结果。
5. 测试期间分别统计首次合格、有限返修后合格、无需管理员介入交付、失败归因、各阶段 P50/P95 和费用。21 条首轮样例不足以证明长期 95% 稳定率；若采用该目标，需要独立更大样本继续验证。
6. 真实任务与故障注入完成后做 72 小时运行观察。发布要求所有承诺输入路线均有真实通过记录、已知高优先级故障关闭、权限/数据/重复提交测试无已知失败，并如实记录仍需人工处理的外部异常。

速度改进以测量为依据：复用已完成观察、减少模型回合、后台按时间查询、独立检查并行、避免整条任务重跑。远端生成时间与本地调度时间分开报告，供应商基线未测出前不承诺固定几分钟完成。

## 本轮交付物及需要补齐的条件

交付物：代码及必要迁移、独立启动脚本、版本预览页面、逐阶段日志/耗时、故障复现测试、实际验收视频与记录、干净源码包、同事部署和恢复说明。

本地代码修复、媒体处理与隔离测试可以立即推进。参考生成真实验收需要可用的持久素材地址；批量收费验收需要费用上限和供应商额度；公司环境验收需要同事提供部署环境。执行到相关阶段前集中确认这些条件，不把未具备条件的阶段写成已完成。

建议执行顺序：第一步完成后，以第二步保障外部任务、第三步保障可见结果；第四步形成可靠短视频闭环，再扩展第五步全部输入和时长；第六步随代码成熟推进，最后按统一标准验收。每一步必须产出可复现证据，不能只报告“测试通过”。
