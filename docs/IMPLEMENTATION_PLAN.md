# Hypit 视频服务生产化代码实施计划

日期：2026-09-27

本文是待执行的实现计划，不代表功能已经完成。依据当前 hypit-agent 代码和实际失败记录制定。

## 1. 交付目标与范围

员工登录公司服务，提交文字、图片、本地参考视频或它们的组合后，系统自动理解素材、规划内容、生成片段、检查、合成并交付视频。正常任务无需手动反复继续；异常有明确状态、恢复路径和管理员处理入口。

覆盖七种非空输入组合：文字；图片；视频；文字＋图片；文字＋视频；图片＋视频；文字＋图片＋视频。无文字时采用界面明确说明的默认意图，只有影响结果的必要歧义才追问。

保留目前的时长交互：自动、8/15/20/30/45/60 秒；自动且有参考时跟随参考时长，自动且无参考时由系统规划。严格时长和约 ±1 秒模式分别验收。参考文件仍允许最长 180 秒、最大 150 MB、图片最多 6 张；长参考完整制作能力必须验收到边界，不能只验证上传。时长和生成单元限制以实际供应商能力核验为准，不能把前端可选项当作供应商已支持。

首轮范围是商品、玩偶、场景。真人出镜、社交平台链接解析、用户指定片段修改不在本轮。制作过程中的自动定向返修属于本轮。

## 2. 当前证据与主要缺口

- 当前小鸡任务在视频提交环节记录 `SUBMISSION_UNCERTAIN: fetch failed`：没有可靠远端回执，不能当成明确拒单直接重发。
- 理解模型请求出现超时和连接断开；本机代理设置不是生产网络方案。
- 图片创作主体理解规则刚修正并完成一次真实识别；不能据此判定完整视频流程验收通过。
- 参考素材依赖的临时公网通道已失效，当前 reference_ready 为 false。
- Web 服务启动内部工作线程，任务主要保存在 SQLite 的 JSON 文档中；不具备多进程任务租约与独立工作进程管理。
- 已有令牌登录、所有权检查和配额基础，尚未完成生产账号、运维与多人验收。
- 现有 72 项测试可作为回归基础，不能替代真实供应商和成片质量验收。

## 3. 实现原则与目标结构

保留已可复用的 Hypit 工程、FFmpeg 处理、素材证据、连续性校验和真实审片能力。新任务统一使用当前制作协议；历史任务保留读取和安全恢复能力。

目标调用关系：浏览器 → HTTPS/API → PostgreSQL；独立 Worker 从数据库领取步骤 → 理解/生成供应商 → 私有对象存储 → 验收与成片下载。

- API 接收请求、鉴权、展示状态，不负责在自身进程里跑长任务。
- 数据库保存任务、步骤、提交意图、远端 ID、租约、用量和事件。初期以 PostgreSQL 队列执行，不同时引入第二套消息队列。
- Worker 执行明确步骤。模型负责理解、规划和判断，代码负责状态迁移、预算、重试、领取和提交权限。
- 等待远端任务通过 next_poll_at 调度，释放执行槽位；限制本地工作并发和远端生成并发，二者分开配置。
- 外部收费请求无法靠本地代码单方面保证恰好执行一次；幂等或查询能力不足时保留“提交待核对”并通知管理员。

## 4. 分阶段代码计划

### P0：建立可重复的故障诊断与供应商能力基线

修改：`app/config.py`、`app/planner.py`、`app/hypit_adapter.py`、`provider-autodl-wan/`、`app/recovery.py`。

新增建议：`app/errors.py`、`app/provider_health.py`、`scripts/probe_provider.py`。

实施：
1. 统一结构化错误：网络连接、认证、限流、输入不支持、明确拒单、生成失败、提交结果不明、审片服务异常、内容不合格。
2. 保留 provider、阶段、请求 ID、耗时、重试次数和脱敏错误；前端不再只显示 Harness 退出码。
3. 从实际部署网络验证文本理解、图片理解、文字生视频、图片生视频、视频参考各条链路；验证真实支持的时长、画幅、声音和输入组合。
4. 对当前不明提交先查本地提交日志和供应商可用记录；不能找回时明确记录无法确认，不删除标记后重发。
5. 将固定超时、重试和代理设置集中配置，生产不依赖员工电脑代理。

交付与门槛：供应商能力表、真实探测记录、错误分类测试。当前供应商若缺少必需能力或连接无法稳定运行，必须先解决服务配置或验证替代接入，不能继续按“已支持”推进。

### P1：持久数据、任务状态机与独立 Worker

修改：`app/store.py`、`app/worker.py`、`app/server.py`、`app/agent_runner.py`。

新增建议：`app/db/`、`migrations/`、`app/task_service.py`、`app/state_machine.py`、`app/worker_main.py`。

实施：
1. 建立 users、assets、jobs、job_steps、generation_attempts、artifacts、events、quota_reservations 表；大体积观察结果保存在存储中，数据库保留索引和版本。
2. 状态覆盖排队、素材理解、规划、提交、等待生成、片段审查、合成、成片审查、完成，以及等待用户、待核对、失败、取消。
3. 步骤领取采用数据库锁、租约、心跳、版本号和事务；租约过期先恢复外部任务记录，再决定是否重新执行。
4. 持久保存每步输入摘要、输出版本、尝试次数和执行耗时；素材或计划变化时使相关后续审核失效。
5. 将队列循环从 API lifespan 移出，Web 重启不停止正常生成；Worker 重启继续查询既有远端任务。
6. 提供带版本的 SQLite 迁移脚本，保留任务 ID、文件与提交日志；维护窗口内停止新提交、备份、迁移、核对数量和文件哈希，再切换。
7. 迁移回退以恢复旧版本和备份为基础；新系统产生收费提交后不可直接恢复旧库丢失新回执，必须先停止领取并对账。

交付与门槛：重复领取、租约过期、进程崩溃、数据库暂时不可用、Web/Worker 重启测试通过；同一步不重复执行收费提交。

### P2：可靠提交、自动恢复与用量管理

修改：`app/hypit_adapter.py`、`provider-autodl-wan/`、`app/recovery.py`、`app/workflows.py`。

新增建议：`app/submissions.py`、`app/quota.py`。

实施：
1. 发请求前事务保存提交意图及固定请求摘要；请求成功后立即保存供应商任务 ID。记录本地 Build ID 和供应商任务 ID 的对应关系。
2. 供应商支持幂等键时复用同一键；不支持时，连接中断进入待核对，不假设请求未发送。
3. 已知任务只查状态、下载或重试检查；不再通过重复提交恢复查询失败。
4. 理解、查询、下载等可重试操作采用有限退避和抖动；明确区分读取失败与新生成请求。
5. 429 按服务端重试信息调度；认证和参数错误停止重试；连续服务故障暂停新的提交并告警。
6. 生成时长预算、并发额度、用户配额在数据库中原子预留。请求不明时保持预留，明确拒绝后按规则释放；供应商实际费用单独记录，不把预留秒数当账单。
7. 增加安全取消和管理员核对入口。取消本地任务不承诺取消已发生费用；远端取消以供应商能力为准。

交付与门槛：模拟“对方已收单但本地断线”“收到回执前重启”“429”“下载失败”“重复点击”等情况，记录完整且不会盲目产生重复收费任务。

### P3：七种输入与时长规则跑通完整制作

修改：`app/intent.py`、`app/subject_spec.py`、`app/reference_analysis.py`、`app/unit_planner.py`、`app/continuity.py`、`app/workflows.py`、`app/production.py`、`app/agent_runner.py`。

实施：
1. 显式区分原创与参考复刻。素材观察给出身份事实，文字给出新动作与场景；原图不必已包含目标动作。
2. 为无文字、无图片和只有参考等情况定义一致的默认意图；多主体对应确实不明时暂停追问。
3. 纯文字跨段创作需要主体一致时生成并复用主体资产；检查相关生图权限，不能运行到中途才发现缺配置。
4. 用结构化计划表达事件、镜头、生成单元、主体绑定、参考区间、依赖、音轨和目标时长，并进行代码校验。
5. 用户固定时长优先，自动模式将实际规划时长写入数据库和页面；明确严格模式的帧级允许误差、近似模式的上下界。
6. 参考内容与固定时长冲突时采用有说明的适配规则；无法同时满足内容完整和指定时间时请求必要选择，不静默删动作。
7. 根据已核验模型限制拆分，支持长参考覆盖；连续单元绑定通过检查的真实衔接帧和主体图。
8. 减少依赖模型决定“下一步做什么”：已完成观察、等待生成、收集输出和标准合成由状态机驱动；保留有边界的模型规划与返修判断。

交付与门槛：七种输入都完成真实成片；覆盖自动、所有手选时长、严格/近似模式，以及参考 180 秒边界。每条样例保留原始素材、计划、实际请求、输出和验收记录。

### P4：画面、声音和成片质量闭环

修改：`app/unit_review.py`、`app/candidate.py`、`app/media.py`、`app/agent_tools.py`，以及现有整片审查实现。

实施：
1. 分离确定性检查与模型检查：文件可解码、分辨率、时长、音轨是否存在由代码验证；主体外观、动作和参考事件覆盖由模型审查。
2. 区分“审片接口没连上”和“视频内容不合格”；前者重试审片，不重新付费生成视频。
3. 片段审查保留事件证据，合成后检查拼接点、音频连续性和全片覆盖；不因候选能播放就标记合格。
4. 返修仅针对有证据的问题单元，并受次数、生成预算和总耗时上限约束。依赖片段变更后重新验证后续衔接。
5. 达到返修上限保留候选并交管理员，说明未满足项，不无限循环。
6. 用人工复核校准自动审片的漏判与误判，特别检查主体错换、动作缺失、明显变形、音轨异常和参考遗漏。

交付与门槛：已知错误样例能拦截，已知合格样例不过度返修；自动判定与人工结果同时记录。成片必须通过当前版本的全部必需检查才能标记完成。

### P5：公司账号、权限、前端与多人调度

修改：`app/auth.py`、`app/server.py`、`static/index.html`、`static/app.js`、`static/style.css`、`app/worker.py`。

新增建议：`app/admin.py`、账号/权限和并发集成测试。

实施：
1. 从环境变量令牌名单升级为可管理账号，具备员工/管理员角色、禁用、登出和会话失效；如公司有现成统一登录，接入统一身份。
2. 生产模式缺认证配置时拒绝启动，不回退为所有人共用 local 用户。
3. 全面检查任务、素材、视频、片段、下载、恢复、候选合成及事件接口的所有权；管理员访问记录审计日志。
4. 使用 HTTPS 安全 Cookie、登录限流、跨站请求防护和明确跨域策略；密钥不下发浏览器。
5. 公平队列和每用户并发上限，避免一个人占满生成资源；按供应商额度控制全局并发。
6. 页面显示输入模式、时长来源、排队/当前步骤、等待原因、可恢复问题、结果与未通过项；耗时估计只有在有实测依据后展示。
7. 增加管理员异常队列、供应商连通状态和提交核对界面。员工不需要读底层日志解决服务故障。

交付与门槛：多账号并发不串素材、不越权、不丢任务；自动时长和重试不能绕过配额；浏览器重复提交不创建重复委托。

### P6：生产部署、持久素材与运维

新增建议：`deploy/`、`scripts/backup.*`、`scripts/restore.*`、`docs/operations.md`；修改 `app/config.py`、`app/media_gateway.py`。

实施：
1. 部署到持续运行的公司服务器，配置固定域名、HTTPS、API、独立 Worker、PostgreSQL 和进程管理。固定依赖版本，生产配置启动时完整校验。
2. 原始素材和结果使用私有持久对象存储；通过供应商能够访问的签名地址供模型读取。签名有效期覆盖真实排队与抓取时间，失败后重新签名须遵守原提交核对规则。
3. 验证供应商实际 GET/Range 读取，而不只看健康接口有 URL；上传格式、大小、时长在入口校验。
4. 区分存活检查、就绪检查和供应商健康状态；就绪检查不执行收费生成。
5. 统一结构化日志和指标：排队时长、各步耗时、失败率、待核对数、远端任务数、存储空间、费用记录。告警只发送到后续指定的公司渠道。
6. 加入清理策略、密钥轮换、数据库一致性备份和素材备份；实际演练恢复，不只确认备份文件存在。
7. 同一生产基础设施先使用隔离验收账号、目录和任务标签验证，再开放员工使用；发布过程停止新领取、保留远端任务并滚动恢复，准备应用版本回退方案。

交付与门槛：固定地址访问、真实素材读取、重启恢复、备份还原、权限、健康检查和告警链路通过生产环境验收。

### P7：真实验收与开放使用

新增建议：`tests/e2e/`、`scripts/acceptance.py`、`docs/acceptance/`。

实施：
1. 建立固定素材集，覆盖七种输入、简单与复杂动作、横竖/方形画幅、长短视频、音轨、多个主体及必要追问。
2. 第一轮每种输入至少 3 条真实样例，共至少 21 条；后续按时长与边界补齐。该数量是首轮功能门槛，不足以证明长期稳定率。
3. 分别测试 2/5/10 个账号同时提交，验证排队与公平性；账号并发不等于同时运行 10 个付费生成，实际执行并发遵循供应商额度。
4. 故障注入覆盖 DNS/连接断开、响应丢失、429、Worker 被终止、数据库短时不可用、签名到期、空间不足和审片服务故障。
5. 验收记录包括软件版本、供应商、输入类型、目标时长、步骤耗时、远端回执、实际用量、输出文件和人工结论。
6. 按生产额度运行至少 72 小时观察，包含真实任务和空闲恢复；报错必须归因和闭环。期间限制验收预算，超过预算停止新提交并保留任务。

交付与门槛：输出逐项通过/不通过清单、遗留项和发布结论。未通过的已承诺核心功能不得标成完成或用别的模型历史样例替代。

## 5. 建议验收指标（待基线实测后定稿）

| 指标 | 建议门槛与统计方法 |
| --- | --- |
| 功能覆盖 | 七种输入、全部界面时长与边界样例均有当前版本真实证据 |
| 自动交付率 | 正常支持范围样例建议目标 ≥95%；从提交到交付无需人工救场，必要的需求追问另列；报告样本数和失败原因 |
| 成片合格率 | 人工按预先定义的主体、动作、参考覆盖、声音、时长标准复核；建议目标 ≥95%，分别统计首次及有限返修后结果 |
| 数据与权限 | 验收中任务丢失、跨用户访问、已知重复收费提交均为 0；不能据此承诺外部服务绝对不会重复处理 |
| 恢复 | 已知远端任务在重启后自动恢复查询；未知提交明确进入核对流程，不能盲重发 |
| 耗时 | 按输入类型和成片时长报告排队与执行 P50/P95；在供应商基线测出前不承诺固定分钟数 |
| 服务可用性 | 建议月度目标 99.5%；72 小时观察不能证明月度指标，需持续监测；Web 可访问与生成依赖可用分别统计 |

## 6. 执行顺序与发布纪律

P0 → P1 → P2 → P3 → P4 → P5 → P6 → P7。生产服务器、域名、对象存储和供应商额度准备从 P0 同步开展；P6 负责完整部署和运维验收。

每阶段交付代码变更、迁移/配置说明、适当的测试及真实验证证据。涉及收费生成的真实验收使用明确的批次、预算上限和任务标记。先解决当前提交不明与供应商能力问题，再扩大样例和多人并发。

不能保证外部模型永不失败；实现目标是正常任务可靠完成、失败分类准确、可安全恢复、结果质量可核对。

## 7. 实施开始时需要确定的部署信息

- 公司生产服务器或云账号、操作系统与访问方式；服务是内网使用还是经公网认证访问。
- 固定域名、证书和对象存储配置。
- 预计员工数、峰值同时提交人数和每日生成量。
- 使用现有公司登录还是应用独立账号。
- 供应商账号权限、并发/限流额度、验收与日常费用上限。
- 告警接收渠道、数据保存周期和备份恢复目标。

这些信息影响部署、容量和验收费用，不阻碍先实施错误分类、状态机、提交记录和输入流程改造；缺少实际环境时不得宣称生产部署已完成。
